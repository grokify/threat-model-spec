# PDLC Threat Modeling — Stage Analysis Reports and Agent Workflows — FAQ

## General Questions

### What is PDLC Threat Modeling?

An extension of the Threat Model Spec JSON IR that makes threat models lifecycle-aware. Instead of a snapshot of an already-built system, a threat model becomes an accumulating security record: agents analyze the artifacts available at each PDLC stage (product-definition, builder-definition, implementation, deployment, builder-operations, product-operations), write structured claims with evidence into the IR, and LLM judges grade the results with stage-specific rubrics before humans act on them.

### Who is this for?

- **Security engineers** who need continuous threat modeling that keeps pace with AI-accelerated development
- **AI agents / analysis pipelines** that produce and consume structured security findings
- **Product and platform teams** assessing their own products (all artifacts available), third-party vendors (docs + live site only), or open-source dependencies (docs + code)
- **Tool builders** who want a vendor-neutral interchange format for security-analysis results

### What problem does it solve?

Three gaps: (1) threat models go stale the moment code diverges from design; (2) results from spec reviews, SAST, DAST, red teaming, and SOC operations live in disconnected tools with no common format; (3) LLM-generated security findings are unverified prose — plausible, but ungraded and hard to trust.

### How is this different from existing threat modeling tools?

Threat Dragon, IriusRisk, and similar tools are GUI-first and snapshot-oriented. SARIF standardizes static-analysis output but has no threat, asset, or lifecycle semantics. OTM (Open Threat Model) covers architecture description but not evidence, analysis runs, judge grading, or stage gates. Threat Model Spec is the only format designed as an IR for agent-produced, judge-graded, evidence-backed analysis across the full lifecycle — while still rendering diagrams (D2) and exporting STIX 2.1.

### Does Threat Model Spec perform the analysis itself?

Threat Model Spec is **first** a data format/IR — that is the foundation and the primary deliverable. Built on it, the project **also enables** analysis: it ships a `tms analyze` command that AI coding agents invoke, plus agnostic agent/workflow specs (authored in `multi-agent-spec`, with Claude Code / Kiro / Gemini plugins generated by `assistantkit`). The analytical reasoning is performed by the AI agent; Threat Model Spec supplies the command surface, the agent/workflow specs, the structured output target, and the LLM-as-Judge grading. It does not reimplement SAST/DAST/SCA scanners — it *consumes* their output — and it is not an autonomous hosted analysis service.

### Isn't shipping Claude Code specs at odds with being vendor-neutral?

No, because the agent specs are themselves vendor-neutral. Per-stage workflows are authored once as agnostic `multi-agent-spec` definitions; `assistantkit` generates the Claude Code, Kiro, and Gemini plugins from them. Claude Code is one generation target, not a privileged hand-authored path — the same way the JSON IR is neutral and D2/STIX are generated views.

### How does `tms analyze` work if the format doesn't do the reasoning?

`tms analyze` is an orchestration entry point, not an analyzer. When an AI coding agent runs `tms analyze --stage builder-definition`, the command loads the stage's report profile, resolves the declared input artifacts against the artifact-availability profile, and hands the agent the workflow spec to execute; the agent does the analytical reasoning and `tms` writes the resulting analysis run (findings, evidence, claims) back into the model, then grades it against the stage rubric. The reasoning is the agent's; the orchestration, structured output, and grading are the tool's.

## Features and Capabilities

### What does a stage analysis report contain?

Each stage has a defined report profile:

| Stage | Report contents |
|-------|----------------|
| Product Definition | Assets, actors, abuse cases, security invariants, prohibited outcomes, privacy requirements |
| Builder Definition | Components, data flows, trust boundaries, STRIDE/LINDDUN threats, required controls, validation plans, API-contract drift |
| Implementation | Evidence-backed findings, design-drift assertions, control verification; ASPM domains 1–5 (git posture, code security, secret/PII scan, open source security, SBOM) |
| Deployment | Runtime exposure, exploitability results, configuration findings, deployed-control verification; ASPM domains 6–9 (IaC scan, CI/CD posture, container security, artifact security) |
| Builder Operations | Detection coverage, incidents, observed techniques, control effectiveness; ASPM domain 10 (cloud context) + dynamic testing (DAST/pen test/red team) |
| Product Operations | Production abuse/fraud signal, adoption-driven risk changes, drift between the shipped product and its Product Definition security invariants |

### What are artifact-availability profiles?

Declarations of which source artifacts exist for a given analysis target, which determine which stage analyses are possible:

- **first-party** — specs, code, IaC, deployment manifests, telemetry: all stages
- **third-party** — public documentation and a live site: product-definition analysis from docs, deployment/operations analysis from external observation; no implementation-stage evidence
- **open-source** — documentation and source code: product/builder-definition analysis from docs, implementation analysis from code; no deployment or operations visibility

A report always records which profile produced it, so consumers know its evidence basis.

### How are LLM-generated findings kept trustworthy?

Via structured-evaluation integration: each stage has its own rubric (LLM-as-a-Judge categorical + 1–5 scoring with findings and reason codes), factual claims are extracted and verified against cited evidence (claims reports), and deterministic checks aggregate into GO/NO-GO stage-gate summaries. Judges can return "insufficient evidence" rather than being forced to accept or reject. Judge identity, model, and rubric version are recorded on every assessment.

### What are framework reports?

Framework-specific projections of one threat model, held in the IR and exportable: STRIDE classification/coverage, LINDDUN privacy view, MITRE ATT&CK technique mapping, OWASP checklist, attack-tree analysis. Frameworks are views over one canonical model — never separate source-of-truth documents.

### What can't it do? (Limitations)

It cannot guarantee semantic completeness — a valid document can still omit the most important trust boundary. The analytical reasoning is the AI agent's, not the format's, so results are only as good as the agent and the evidence available to it. It does not replace dedicated SAST/DAST/SCA scanners (it consumes their output) and does not embed bulk operational data (SIEM logs are referenced with queries, time windows, and digests, not stored).

## Technical Questions

### Is this backward compatible?

Yes. Existing `assets`, `scenarios`, `diagrams`, `mitigations`, and `detections` are preserved. Lifecycle objects (`artifacts`, `analysisRuns`, `evidence`, `securityRequirements`, `architectureAssertions`, `gates`) are additive and optional. The singular `phase` field is deprecated but retained. Ships as the next schema version.

### Where are the PDLC stages defined?

In the ProductBuildersHQ PDLC ecosystem. The six stages are defined machine-readably in the `productbuildershq-frameworks` PDLC catalog entry (the six-stage split of AWS AI-DLC's three phases) and re-exported by the `pdlc` module; the pdlc repository's `lifecycle.md` is the normative narrative. Threat Model Spec imports those stage IDs rather than inventing its own.

### Does Threat Model Spec need to understand every spec workflow (aws-one-way-door, pbhq-lite, big-tech, …)?

No — and this is the key simplification. Threat Model Spec analyzes by the six PDLC stages, not by individual spec types. The mapping from concrete spec types to PDLC stages lives in `specification-workflow-spec` (which tags each spec type with a `PDLCStage` — PRD → product-definition, TRD → builder-definition, and so on; only the two spec-driven stages appear there). Given any workflow, Threat Model Spec buckets its specs into the stages via that registry and runs the per-stage analysis. A new workflow, or a new spec type, needs **zero** Threat Model Spec changes as long as it's categorized upstream. Threat Model Spec only ever reasons about "the product-definition-stage artifacts," never "PRD.md specifically."

### How does structured-evaluation fit in? Does it need changes?

threat-model-spec already depends on `plexusone/structured-evaluation` (rubric, claims, summary packages). Per-stage evaluation needs are met with new *rubric definitions* (data, not code). Candidate library extensions being assessed: evidence-locator types for security claims (file+line, manifest path, log query), stage/profile metadata on report envelopes, and an explicit "insufficient evidence" verdict if the current verdict taxonomy lacks it.

### How do reports get stored and audited?

The IR is file-first (JSON in git). For multi-judge pipelines, assessments can be persisted in DoltDB with append-only judge-run and assessment tables, with Dolt commits as a second audit layer binding judge runs to row-level changes.

## Tough Questions (Internal Vetting)

### Why would customers NOT use this?

Teams with an established GUI tool and no agent pipeline get less value — the payoff comes from automated producers/consumers. Adoption requires writing or adapting agents. The format is pre-1.0 and evolving.

### What would disappoint customers most about v1?

Agent workflow definitions ship as specifications, not turnkey runnable agents. Coverage guarantees are structural (did every entity/framework combination get considered), not semantic (did we find everything).

### What's the hardest technical challenge?

Keeping the IR's claim/evidence model simple enough for agents to fill correctly while rich enough to distinguish threat, vulnerability, finding, evidence, and incident — and making judge grading discriminating rather than rubber-stamping.

### What would make this fail?

If the schema grows faster than producers adopt it (spec-without-implementations), or if judge grading proves uncalibrated so humans re-review everything anyway. Mitigations: dogfood on our own repos each phase; seed calibration vulnerabilities to measure judge quality.
