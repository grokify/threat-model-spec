## Threat Model Spec Announces Lifecycle Threat Modeling: Continuous, Evidence-Backed Security Analysis from Product Definition to Production

**San Francisco, CA** — The Threat Model Spec project today announced PDLC Threat Modeling, a lifecycle-aware extension of its open-source threat modeling format that lets AI agents and security teams produce evidence-backed threat analysis reports at every stage of the product development lifecycle — product definition, builder definition, implementation, deployment, builder operations, and product operations — all accumulating into one continuously refined threat model.

Teams shipping with AI-accelerated development generate code faster than security review can keep up. PDLC Threat Modeling turns threat modeling from a one-time diagram exercise into a standing analysis pipeline: agents analyze whatever artifacts exist at each stage, write structured findings into the Threat Model Spec JSON IR, and LLM judges grade every claim against stage-specific rubrics before it reaches a human.

## The Customer Problem

"Our AI agents write a week's worth of code in an afternoon, but our threat model was a diagram we made at design time and never touched again," said a platform security lead at a mid-size SaaS company. "By the time we did a security review, the design assumptions and the deployed system had drifted apart — and nobody could say which threats were still real, which were mitigated, or what evidence backed any of it."

Security teams face three gaps: threat models describe a moment in time, not a living system; analysis results from spec reviews, SAST, DAST, and SOC operations live in disconnected tools with no shared format; and LLM-generated security findings are plausible-sounding but ungraded, forcing humans to re-verify everything.

## The Solution

PDLC Threat Modeling extends the Threat Model Spec IR with lifecycle semantics: source artifacts, per-stage analysis runs, evidence-backed claims, and stage gates. For each PDLC stage — codified in the ProductBuildersHQ PDLC specification — the format defines what a Threat Model Spec Analysis Report contains, what input artifacts it requires, and the agent workflow that produces it:

- **Product Definition stage:** assets, abuse cases, security invariants, prohibited outcomes
- **Builder Definition stage:** trust boundaries, STRIDE/LINDDUN threats, required controls, validation plans
- **Implementation stage:** evidence-backed findings, design drift detection, control verification (ASPM: code, secrets, dependencies, SBOM)
- **Deployment stage:** runtime exposure, exploitability, configuration findings (ASPM: IaC, CI/CD, containers, artifacts)
- **Builder Operations stage:** detections, incidents, control effectiveness (ASPM: cloud posture, plus DAST/red team)
- **Product Operations stage:** production abuse signal and drift from the product's security invariants

Analysis adapts to what you have. First-party products supply artifacts at every stage; a third-party vendor assessment may have only documentation and a live site; an open-source dependency review has documentation and code. The format's artifact-availability profiles tell agents which analyses are possible and which reports they can credibly produce.

Every report is graded before it's trusted. Integration with the structured-evaluation framework gives each stage its own LLM-as-a-Judge rubric, verifies factual claims against cited evidence, and rolls results into GO/NO-GO stage-gate summaries. And because frameworks are views over one model, any threat model can export framework-specific reports — STRIDE coverage, LINDDUN privacy analysis, MITRE ATT&CK technique mapping, OWASP checklist — from the same JSON IR.

## Getting Started

PDLC Threat Modeling ships in the Threat Model Spec open-source repository (MIT license) as versioned JSON Schemas, Go types, per-stage rubrics, agnostic agent/workflow specs (authored in `multi-agent-spec`, with Claude Code / Kiro / Gemini plugins generated by `assistantkit`), and the `tms analyze` command those agents call — with the lifecycle stages specified in the ProductBuildersHQ PDLC repository. Existing threat models remain valid; lifecycle fields are additive.

The `tms analyze` command is invoked by an AI coding agent such as Claude Code: the agent does the analytical reasoning, and `tms` loads the stage profile, gathers inputs, writes the analysis run into the model, and grades it. Threat Model Spec is first a format; the analysis layer is built on top of it.

```bash
go get github.com/grokify/threat-model-spec
# invoked by an AI coding agent (e.g. Claude Code) running the builder-definition workflow:
tms analyze threat-model.json --stage builder-definition --profile first-party ./docs/specs/
```
